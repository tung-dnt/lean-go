# Constraints

This is the single rulebook for people and AI agents: `AGENTS.md` only points here. Read it before writing code. Do not weaken it to make a change pass: tightening is silent, loosening needs the owner's explicit OK in the PR.

When you start a project from this template, put your name and the date on the line below, and fill in the Measured and Exceptions tables as the project gets real numbers.

Last reviewed: _(date)_ by _(owner)_.

## Stack

- Go standard library first; a dependency has to earn its place. HTTP is `net/http` with `http.ServeMux` (method + path patterns). No router framework, no ORM, no DI container, no reflection-driven wiring, no `init()` registration.
- Data access is sqlc over raw SQL in `internal/external/db/queries`, against the schema in `internal/external/db/migrations` (golang-migrate, versioned; production migrates with the `migrate-*` just recipes or the `migrate/migrate` image). The generated code is in `internal/external/db`: never hand-edit it.
- Views are gomponents in Go; the browser side is htmx (hx-boost) and Alpine, bundled from npm by esbuild, styled with Tailwind + daisyUI.
- Errors are handled where they happen with an explicit `if err != nil` and wrapped with `%w`. No ignored errors (`_ = f()`), no `panic` for control flow, no empty error branches.
- No interface that exists only so a test can fake it. Tests run the real server against a real PostgreSQL.

## Layout

```
cmd/<binary>/        entrypoints only: parse config, build, run. No business logic.
internal/<domain>/   one flat package per domain, split by concern, no sub-packages:
                       <domain>.go        types, rules and handlers
                       views.go           what the domain draws
                       state.go           only if the domain keeps state worth its own file
                       <domain>_test.go   end-to-end tests
                     split a file further only once it passes ~800 lines
internal/server/     Run, NewServer (the middleware every page goes through), routes.go (every route)
  paths/               the typed path of every route; the one server package a domain or internal/ui imports
internal/ui/         the page shell: layouts, components, icons, request helpers
internal/external/   adapters over third-party services, and the database:
  db/migrations/       golang-migrate up/down files (db/embed.go embeds them in the binary)
  db/queries/          the SQL that sqlc turns into Go
  db/                  GENERATED by `just sqlc`
pkg/                 shared, domain-agnostic code (config, log, middleware, form, session, ...)
web/js/              the TypeScript that `just js` bundles, cut into areas the way internal/ is cut into domains
```

A domain imports `pkg`, `internal/ui`, `internal/external`, `internal/server/paths`, and no other domain unless the edge is listed in `domains` of `internal/architecture_test.go`. `pkg` and `internal/external` import no domain, no `internal/server` and no `internal/ui`; `internal/ui` imports no domain and nothing of `internal/server` but `internal/server/paths`, which imports nothing of the module; only `internal/server` imports the domains, and `cmd/*` imports only the server, `pkg`, and `internal/external` (plus the edges of `cmdAllowed`: `cmd/admin` also imports `auth`). The libraries the standard library replaced (echo, gorilla, go-playground/validator, chi) are not imported anywhere, and a third-party SDK only under `internal/external`. `internal/architecture_test.go` holds all of it, and the same for the imports of `web/js`.

## Server conventions

The recipe for adding a domain to the server. `internal/note` is the worked example (a list, a form, a page, an admin action); `internal/auth` is the second. Read `internal/server/server.go` (the middleware every page goes through, in order) and `internal/server/routes.go` (every route) once before you start.

- **Handler maker.** A handler is made by `HandleX(deps...) http.Handler` that takes only the dependencies it uses and does its one-time preparation in the closure; it is not a method on a struct. A page that needs nothing takes nothing (`auth.HandleLogin`); one that reads the database takes `*db.Queries` (`note.HandleList`). In a handler `r` is the `*http.Request`; the `*ui.Request` a view is drawn from is `page := ui.NewRequest(r)`.
- **Errors.** Every failure ends in `layouts.Error(w, r, err)` followed by `return`. It logs (5xx as error, 4xx as warning), picks the status and draws the error page: `*httperr.Error{Status, Message}` for a status of your own (`httperr.New(http.StatusNotFound, "no such note")`), `*http.MaxBytesError` for 413, a request that ran out of time for 503, a client that left for nothing, anything else for 500. Never `http.Error`, never write an error status yourself. Wrap what you return with `%w` and the step that failed. Only a 413 shows its `Message` on the page (give it the domain's words); no other message is ever shown.
- **Rendering.** `ui.Render(w, page, layouts.Primary, node)`; for a status other than 200 `ui.RenderStatus(w, status, page, layout, node)`. Never call `w.WriteHeader` before rendering: the flash messages are taken out of the session while the page is built, and the cookie that says so goes out with the headers. A render error goes to `layouts.Error` (`note.draw`). Views import gomponents as `g`/`h` and the components package qualified: no dot imports.
- **Forms.** A form is a struct with `form:"name"` tags that embeds `form.Submission` and has `Valid(ctx) map[string]string` (keys are the Go field names, values the sentence shown under the field; `note.noteForm`). `form.Decode(r, &in)` fills it from a url-encoded or multipart body (never from the query string), runs `Valid`, and fails only for a body that cannot be read (400/415, or the `*http.MaxBytesError` for a 413); then `in.IsValid()` says whether to draw the form again (`note.HandleCreate`). What only the handler can know goes in with `in.SetFieldError("Field", "...")`. Decode reads at most 1 MiB; the route that takes more says so with `middleware.LargeBody` (below). Files of a multipart body are read with `r.FormFile` after Decode, and `form.Cleanup` (in NewServer) removes the temporary files. Messages: `required` is `form.MsgRequired`, an email check is `form.IsEmail` + `form.MsgEmail`; there are no `validate:` struct tags. A limit the form checks is also a `CHECK` of the table (migration `000002_notes`).
- **Paths.** Never spell a path in a link, a form action or a redirect: `paths.Note(id)`, `paths.Home` (`internal/server/paths`). A new route adds its path there and a row to `routes` in `internal/server/paths_test.go` (and to the wildcard table when it has a `{wildcard}`); the test fails for a path that leads nowhere.
- **Session, flash, redirect, user.** `msg.Success(r.Context(), "...")` (also `Info`, `Warning`, `Error`) and then `redirect.To(w, r, paths.Home, http.StatusSeeOther)`, which answers a boosted htmx request with `HX-Redirect`. A post that worked answers with a 303, so that a reload does not post it again. Who is logged in: `middleware.User(r.Context())`, or `page.IsAuth`/`page.IsAdmin` in a view. Logging in and out is the session: `sess, ok := session.From(r.Context())`, `sess.Clear()`, `sess.SetUserID(id)` (`auth.HandleLoginSubmit`). The session is one AES-256-GCM sealed cookie, written by the middleware only when it changed; a cookie that does not open is an empty session. Domains never import `internal/auth`: the server loads the user (`middleware.LoadUser`).
- **Guards and middleware placement.** The middleware every page goes through are in `NewServer`, outermost first, each with the reason for its place; files and `/healthz` skip them (`isBare`). Per-route middleware is applied in `routes.go`: `requireAuth`/`requireNoAuth` (`middleware.RequireAuth(fail)`), `middleware.CacheControl`, `middleware.GzipFiles`, and, on a route that takes a large body, `middleware.LargeBody(limit, timeout, layouts.Error)(handler)`: it caps the body, moves the read/write deadlines and the request's own deadline for that route only. Everything at or below `/admin` is held to the admin check by `NewServer`, a route nobody wrote yet included, so an admin route needs no wrapper (`POST /admin/notes/{id}/delete`). A get never changes anything: an action is a post. Do not register a page pattern that ends in `/` (the router redirects `/x` to `/x/` and `RemoveTrailingSlash` back).
- **Requests and time.** Pass `r.Context()` to every query and call: the request deadline (config `app.timeout`) cancels it with the cause `httperr.ErrTimeout`, which the error page answers with a 503. Log with `log.Ctx(r.Context())` (it carries the request id). The client address is `middleware.RealIP(r)`.
- **Adding a domain's routes.** In `addRoutes` (`internal/server/routes.go`), under a comment line naming the domain, make the handlers from the fields of `d` and register them: `mux.Handle("GET /notes/{id}", note.HandleShow(d.queries))`, read with `r.PathValue("id")`. `GET` also serves `HEAD`. **Register the home page as `GET /{$}`**: a bare `GET /` is a subtree pattern that takes every GET no other route has, so the 404 page of the catch-all (`mux.Handle("/", HandleNotFound())`) would never be drawn for a GET. A maker only keeps what it is given: `internal/server/paths_test.go` makes the routes from dependencies that are nil, so what is read from one is read when a request is served, not when the handler is made. A new dependency (a client of a third-party service, say) is built in `Run`, passed to `NewServer` and kept in `deps`.
- **Background work.** There is no task queue. Work that cannot finish inside a request is a row in PostgreSQL (its status and attempts) and one goroutine that `Run` starts and stops with its context (`sync.WaitGroup.Go`, waited for before the pool closes). The handler writes the row and wakes the goroutine through a one-slot channel; the goroutine reads what to do from the database, never from the signal. Its first pass after a start runs the rows a dead process left half done, so a run must be idempotent (settle the row and write its result in one transaction that locks the row first). A run that failed for a fault waits a configured backoff before it is run again, without holding the other rows back. Test it end to end, with a restart: `servertest.Start(t, servertest.KeepSchema())`, `srv.Stop(t)`, then `servertest.Start(t, servertest.Sharing(srv))`. See `docs/adr/0002-background-work-goroutine.md`.
- **A large body and its 413.** `middleware.LargeBody(limit, timeout, fail)` turns away a body whose `Content-Length` is over `limit` before it reads a byte and caps the rest with `http.MaxBytesReader`; both come out as an `*http.MaxBytesError`, which `layouts.Error` answers with a generic 413 ("That request is too large. It can be up to N MB."). To say the domain's own words, give `LargeBody` an `ErrorFunc` that wraps the error first, and do the same in the handler for the error `form.Decode` returns: `var tooLarge *http.MaxBytesError; if errors.As(err, &tooLarge) { err = httperr.New(http.StatusRequestEntityTooLarge, "...") }`, then `layouts.Error(w, r, err)`. `LargeBody` also raises what `form.Decode` reads of that body from 1 MiB to `limit`.
- **End-to-end tests.** Tests are in the external package of the domain (`package note_test`), never in the package itself (the server imports every domain, so a test that imports the server from inside would be an import cycle); pure-function tests may stay internal. One `TestMain` starts the real server:

  ```go
  var srv *servertest.Server

  func TestMain(m *testing.M) { os.Exit(servertest.Main(m, func(s *servertest.Server) { srv = s })) }
  ```

  and a test drives it as a browser does: `visitor := servertest.NewVisitor(t)` (cookie jar, no redirect following), `srv.Visit(t, visitor, http.MethodGet, paths.Login)`, `srv.PostForm`, `srv.LogIn`, `srv.LogInAs(t, admin)`, `srv.NewAccount`, `srv.NewRequest`+`srv.Do` for headers, `servertest.Fragment` (goquery). `srv.Queries`/`srv.DB` make rows. `servertest.Start(t, servertest.WithEnv(...))` is a server of its own, with a schema of its own, for a test that must break the database, count every row, or change the configuration. The database is broken at one query, the real one, with `srv.FailQuery(t, table, query)` (the query that sqlc named so fails with "boom" when it reads the table) or `srv.HideRows(t, table, query)` (it finds nothing there, as when a row went between two queries of a request), `srv.Heal(t)` takes the fault away, and `srv.Log()` is what the server logged (take its length before a request and read what comes after). The tests of a package share one database: make what you look for with a name that nothing else has. There is no CSRF token to fetch: a cross-site post is refused by `http.CrossOriginProtection` (a post without `Origin` and `Sec-Fetch-Site`, as a test client sends, is let through). `internal/note/note_test.go` shows each of these.
- **Frontend.** A component is an Alpine component in an area folder of `web/js` (`note/charCount.ts`), registered in `web/js/register.ts` and named in the markup with `x-data`. The `data-*` attributes it reads are its contract with the view: say so in a comment on both sides. A new area, or an edge between areas, is a row in `webAreas` of the architecture test and in README's table.

## Workflow

1. Test first: write the end-to-end test through the real server (real handlers, real PostgreSQL), watch it fail for the right reason, then write the code.
2. Changing data access: `just migrate-new <name>`, edit the SQL in `internal/external/db/migrations` / `internal/external/db/queries`, then `just sqlc`. Commit the regenerated `internal/external/db`. A query whose SQL has a rule of its own (an order, a lock, a limit) gets a test in `internal/external/db`.
3. Finish with `just check` (`sqlc-verify sqlc-vet lint vuln types secrets deps dupes test build`). A task is not done until it is green.

Tests need Docker, nothing else: the first test in a process starts one `postgres:17-alpine` container (`pkg/testdb`) and Ryuk removes it afterwards. CI sets `GO_DATABASE_TESTCONNECTION` to its postgres service instead.

## Floor (always enforced)

- No skipped or deleted tests, and no assertions removed from tests that stay, without a reason in the commit message. A test that pinned markup is rewritten to pin behaviour (roles, `data-*`, ids, text), never dropped.
- No unimplemented stubs: `panic("TODO")`, `// TODO: implement`, functions that return zero values where logic belongs, empty error handling (`_ = err`, `if err != nil {}`).
- No new suppressions: `//nolint`, `// @ts-ignore`, `// @ts-expect-error`, `eslint-disable`, `gitleaks:allow`.
- No secrets in source. `config/config.yaml` holds only local values; a live environment overrides every secret with a `GO_*` variable.
- Go: `go vet ./...` clean, `golangci-lint run` (`.golangci.yml`) reports nothing, and `internal/architecture_test.go` passes (module and web edges).
- This file is not weakened in the same PR as the change that was failing.

Commands run through [just](https://github.com/casey/just) (`brew install just`), from the `justfile`.
